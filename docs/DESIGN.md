## 2. Agent 설계

에이전트는 이 시스템에서 유일하게 양쪽으로 소통한다.
한 쪽으로는 디바이스와 시리얼로 소통하고,
다른 한 쪽은 HTTP로 백엔드와 소통한다.

### 2.1 스레드와 큐

| 스레드      | 하는 일                                                                                      |
|-------------|----------------------------------------------------------------------------------------------|
| `reader`    | 디바이스와 연결 및 연결 유지, 디바이스가 보내는 데이터 한 줄씩 읽어 파싱, 타입별로 큐에 분배 |
| `sender`    | 주기에 맞게 백엔드에 하트비트 전송, 데이터 큐를 읽어와 백엔드에 텔레메트리 전송              |
| `commander` | 백엔드로부터 대기 명령 폴링, 한 건씩 장치에 보내고 처리 결과 받아서 백엔드로 전송            |

#### Thread 사용 이유
두 종류의 통신을 한 루프에 두면, 한쪽이 느려지면 다른 한 쪽에 딜레이가 생긴다.
가령 백엔드 통신이 늦어져서 대기하게 되면, 시리얼 데이터가 버퍼에 쌓이고, 유실될 수도 있다.
주기적으로 계속 데이터를 읽어오고, 전송해야하는 상황이기에, 우선 읽기와 쓰기를 분리했다.

`reader`는 시리얼 데이터를 읽어서 큐에 저장하고,
`sender`는 큐의 데이터를 꺼내서 백엔드로 전송하는 방식이다.
이렇게 되면 백엔드 통신이 멈추어도, 디바이스 데이터를 계속 읽어올 수 있다.

또한 명령 처리를 `commander` 쓰레드로 따로 분리했는데,
이는 스스로 명령의 결과를 기다려야하기 때문이다.
최대 3초까지 대기하는 동안 다른 작업을 진행할 수 없기 때문에 명령 처리를 혼자 단독으로 두었다.

#### Queue 사용 이유
들어온 데이터를 순차적으로 저장하고 처리할 수 있는 가장 간편한 자료구조이다.
또한 쓰레드끼리 공유하는 자원은 상호 배제를 구현해야하는데,
`queue.Queue` 자체가 스레드에서 안전하게 사용할 수 있게 구현되었기에, 따로 락을 구현할 필요가 없다.

### 2.2 디바이스 연결

에이전트는 디바이스와 연결하고, `serial.Serial` 객체 `link`를 통해 통신하게 된다.
에이전트는 `link` 가 `None` 이면 연결을 시도하고, 실패하면 2초 쉬고 다시 시도한다.
데이터를 읽다가 예외가 나면, 연결을 닫고 다시 연결을 시도한다.

재연결에 성공하면 장치가 `HELLO` 를 다시 보낸다. 에이전트는 이때 `POST /devices` 로
재등록한다. 등록이 연결 시점에 묶여 있으므로 펌웨어 버전이 바뀌어도 자동으로 갱신된다.

`link` 는 `reader`와 `commander` 쓰레드가 함께 사용하는 공유 자원이라
`link_lock` 으로 직접 감싸서 사용한다.

### 2.3 명령 처리

명령은 한 번에 하나씩 처리한다. 한 명령의 처리가 끝나야 다음 명령 폴링을 한다.

1. `ack_queue`를 비운다. 전의 다른 명령이 타임아웃된 뒤 늦게 도착한 ACK가 남아 있을 수 있다.
   비우지 않으면 그 잔여물이 이번 명령의 응답으로 오인된다.
2. `CMD`를 디바이스에 전송한다. 쓰기가 실패하면 연결이 끊긴 것이므로
   기다리지 않고 바로 실패로 보고한다.
3. ACK를 기다린다. `device_ack_timeout_sec` 동안 1초씩 끊어 큐를 본다.
   꺼낸 메시지의 `id` 가 다르면 버리고 계속 기다린다.
4. 결과를 분류해 보고한다.
   시간이 끝나거나 응답이 도착하면 상황에 맞게 처리한다.

### 2.4 파서

파서는 디바이스가 전송하는 메시지를 타입별로 `SCHEMA`에 선언해 두고,
하나라도 맞지 않거나 변환에 실패하면 그 줄을 통째로 버린다.


## 3. Backend 설계

### 3.1 Database

모든 엔티티는 `BaseEntity(createdAt,updatedAt)`를 상속한다.

| 엔티티      | 주요 컬럼                                                                         |
|-------------|-----------------------------------------------------------------------------------|
| `Device`    | `deviceId`(unique), `deviceUrl`, `fw`, `lastHeartbeatAt`                          |
| `Telemetry` | `device`(1:N), `seq`, `ts`, `temperature`, `humidity`                             |
| `Command`   | `device`(1:N), `commandId`(unique), `type`, `value`, `status`, `source`, `reason` |
| `Rule`      | `device`(1:1), `metric`, `threshold`, `lastAction`                                |

**연관은 전부 지연 로딩이다.** `Telemetry` 나 `Command` 를 읽을 때 `Device` 를 같이 끌어올
이유가 없다. 응답 DTO도 필요한 필드만 담아 엔티티를 그대로 노출하지 않는다.

**콘솔은 항상 "최근 것부터 N건"을 본다.** 그렇기에 조회는 JPA naming을 통해
`findFirstByDeviceOrderByTsDesc`(최신 1건), 
`findByDeviceOrderByCreatedAtDesc`(최신 N건)과 같은 형식을 사용한다.


### 3.2 백엔드 상세

[API명세서 openAPI.md](./openAPI.md)

입력 형식은 Bean Validation 제약 어노테이션으로 검증한다.
`BackendController`는 요청을 받고 넘기기만 하고,
구체적인 로직은 전부 `BackendService`에 있다.
데이터베이스 쿼리는 `JPARepository`를 이용한다.
`lastHeartbeatAt` 이 30초 이내면 `ONLINE`, 아니면 `OFFLINE` 으로 조회 시점에 판정한다.

규칙은 매 텔레메트리를 저장한 직후 평가한다.
`Rule`에는 `lastAction`이라는 마지막 판정을 남겨 두므로,
그것과 다른 판정이 나올 때만 새로운 명령을 자동으로 만든다.
그렇기에 똑같은 명령이 계속 생성되지 않는다.


## 4. CLI 설계

**상태를 갖지 않는다.**  
명령마다 해당하는 함수를 호출하고, 응답을 출력하고 끝낸다.
세션도 캐시도 없다. 어디서 몇 번을 실행해도 결과가 같다.
하지만 `led` 만 예외로 결과를 추적한다. 명령의 수행 결과까지 출력하고 끝난다.


## 5. 심화 과제 C — 명령 신뢰성

TIMEOUT을 처리하고, 재시도하는 정책을 구현함.

### 5.1 상태

| 상태      | 뜻                                      |
|-----------|-----------------------------------------|
| `PENDING` | 만들어졌고 아직 전송되지 않은 명령    |
| `SENT`    | 에이전트에게 전달된 명령   |
| `ACKED`   | 장치가 수행함. 종료                     |
| `FAILED`  | 장치가 거부했거나 전송에 실패함. 종료   |
| `TIMEOUT` | 제한 시간 안에 결과가 오지 않음. 재전달 대상 |

### 5.2 상세 설명

이 구조에서 **백엔드**는 무조건 모든 명령의 상태를 완료로 만든다.

명령은 무조건 한 번에 한 건씩 주는데, 
그 이유는 에이전트가 어차피 한 번에 하나씩만 처리하기 때문이다.
에이전트는 한 명령의 처리가 끝나기 전 까지 다음 명령을 폴링하지 않는다.

백엔드는 `PENDING`이나 `SENT`인 채로 15초가 지나면 `TIMEOUT`으로 상태를 바꾼다.
에이전트는 `PENDING`과 `TIMEOUT` 둘 다 폴링하기 때문에
`TIMEOUT` 이 된 명령은 다음 폴링에서 다시 나간다.
그렇기에 결국 모든 명령이 종료 상태가 된다.

`led` 명령을 전달한 CLI는 최대 15초 동안 명령 상태를 기다리고, 그 결과를 출력한다.

CLI는 실행 결과를 확인하기 위해 명령 상태를 계속 조회하는데,
이 api 호출을 통해 현재 상태도 확인되고, 내부적으로 `TIMEOUT`도 계산된다.
